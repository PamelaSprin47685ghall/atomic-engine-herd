# modules/kv-capacity — 解耦 KV 容量：判定而不是分配

原分叉给 `llama_context_params` 加了 `n_ctx_kv`：一个独立于逻辑窗口的**物理 KV 容量**。
它的用途不是「更大的缓存」，而是为主序列之外的辅助序列（reader、draft）预留单元，
且**不能**靠放大 `n_ctx` 实现——因为 `n_ctx` 同时决定注意力掩码与最坏情况计算缓冲的大小
（原分叉 `src/llama-context.cpp:954-982`）。

## 纯外挂能否做到：能，且已实测（前两版这里错了两次）

先记下两次错误，因为它们是同一类推理失误，而且第二次是本项目自己推翻的。

**第一次**：「`cparams` 是 const 引用，所以容量不可改写」。**不成立**——const 引用约束的是
被调用者不能改入参，不约束调用者换一个入参。补丁拥有这次调用，完全可以复制一份
`llama_cparams`、改掉 `n_ctx_seq`、再用副本调原函数。这正是 prefab 车道借
`llama_set_embeddings` 重新置位时用的同一手法；参数是不是 const，从来不决定外部调用者能否
换一个值。

**第二次**：「真正的障碍是上游只有一个数，单元就是窗口，所以只能改上游」。**也不成立**，
而且它比第一次更值得记：它听起来像源码结论（`kv_size` 确实同时决定单元数与张量长度），
但它把「一个字段」误当成「一个时刻」。实测见下。

```c
llama_kv_cache::llama_kv_cache(… uint32_t kv_size, uint32_t n_seq_max …)
```

`cparams.n_ctx_seq` 同时是

- KV 单元的数量：`v_cells[s].resize(kv_size)`（`llama-kv-cache.cpp:144`）；
- K/V 张量本身的长度：`ggml_new_tensor_3d(ctx, type_k, n_embd_k_gqa, kv_size, n_stream)`（`:233-234`）。

### 一个字段，两个时刻

上面两条事实（`kv_size` 同时决定单元数与张量长度）是对的；错的是从它们推出的「不可分离」。
`n_ctx_seq` 只有一个字段，但它被**两个不同时刻的两个消费者**读取：

| 消费者 | 读的是哪份 | 决定什么 |
|---|---|---|
| 上下文自己保存的 `cparams` 成员 | 构造时留下的那一份 | `llama_n_ctx()` / `llama_n_ctx_seq()`、解码边界、`get_rope_factors` 的长短 rope 选择 |
| `llama_model::create_memory(model, params, cparams)` | **它拿到的那个引用** | 仅缓存尺寸：`kv_size` 与每层 K/V 张量的长度 |

参数副本只进第二个消费者。所以池子变大、窗口认知不变——这正是分叉 `n_ctx_kv` 想做而
不必新增字段就能做到的事。

第三处也顺带成立：掩码**不是**按容量分配的。`llama_kv_cache::get_n_kv()` 取
`min(cells.size(), PAD(used_max_p1, 256))`，按**在用**单元数算，空余单元不参与。分叉担心的
「最坏情况计算缓冲被放大」是 `n_ctx` 的后果，不是池子的后果。

### 实测（`build/herd-nkv-probe`，tiny transformer，唯一变量 `HERD_NKV_PHYSICAL`）

| 运行 | `n_ctx` | `n_ctx_seq` | `kv_bytes` | 第二序列解码 | logits |
|---|---|---|---|---|---|
| control | 256 | 256 | 98304 | `rc=1`（无单元） | 基准 |
| `HERD_NKV_PHYSICAL=512` | 256 | 256 | **196608** | `rc=0`（有单元） | 逐字节相同 |

`kv_bytes` 来自 `llama_memory_i::memory_breakdown()`，是缓存自己报告已分配缓冲的大小——
翻倍是分配器说的，不是我们回显的传参。窗口不变、logits 逐字节相同（`cmp` 原始 float 转储，
摘要两次都是 `6fa4d541e3436dea`）、越窗解码两次都被拒。唯一改变的正是要紧的那一项：池子
256 时把序列 0 填满窗口后序列 1 无处安放，池子 512 时它得到自己的单元。

**安全性**（已核，非假定）：`create_memory` 把 `cparams.n_ctx_seq` 以**值**传给缓存构造函数
（形参 `uint32_t kv_size`），`llama_kv_cache` 不持有 `cparams` 引用（该类型在头文件里只有
前向声明）。传栈副本因此不会 use-after-return；这是唯一会让该 hook 悬垂的布置，而上游不是
这样。pin 变更任一事实会让实验 TU 编译失败，因为它是包含私有头的。

### 所以本模块的定位

判定与分配是两件事，现在各有归属：

- `modules/kv-capacity`（本包）是**判定**：合法与否、实际数字、用原生参数能否表达。它不分配。
- `patches/herd_nkv.cpp` 是**实验**：证明参数副本能让池子大于窗口且不改变计算。默认不进构建
  （`HERD_BUILD_NKV=OFF`）、不链接任何产品、`HERD_NKV_PHYSICAL` 未设时 hook 不注册。

把实验变成产品，缺的是验证而不是机制（见「未做」）。

## 那这里提供什么

可判定性。给定（逻辑窗口、请求容量、序列数、是否统一缓存、是否精确长度、模型族），
回答三件事：

1. **合法吗** —— 原分叉自己的七条拒绝，逐条附行号；
2. **实际数字是什么** —— 补齐到 256 之后的窗口与容量，而不是请求值；
3. **上游能不能原生表达** —— 这是最有用的一个，见下。

这不是安慰奖。本项目已经反复撞上同一类缺陷：`batch-compose` 把 `--total-kv` 静默压回
`--n-ctx`，`rerot-compose` 把「解耦容量」与其余四项一起笼统拒绝。二者都是同一件事：
**缺少一个能区分「合法但无法表达」与「不合法」的判定**。

## 上游其实能表达解耦容量——在另一种形状里

这是本轮最有价值的结论，它把一个笼统的「不可用」变成了可执行的子集：

| 形状 | 上游参数 | 物理容量 | 逻辑窗口 | 可表达 |
|---|---|---|---|---|
| unified | `kv_unified=true` | `n_ctx` | `n_ctx` | 仅当容量 = 窗口 |
| **split** | `kv_unified=false, n_seq_max=S` | `n_ctx = S × 窗口` | `n_ctx / S` | **是**：每多一个序列就多一个窗口 |
| decoupled（分叉） | `n_ctx_kv` | 任意 ≥ 窗口 | `n_ctx` | **是**：用 `create_memory` 的参数副本（实测，见下）；原生参数做不到 |

也就是说：**「物理容量 = S 个逻辑窗口」今天用原生参数即可得到**，代价是上下文里存在 S 个
序列。分叉额外允许的是「物理容量 > 一个窗口，而序列数仍为 1」——这一条**不必改上游**：
`create_memory` 的参数副本就能做到（实测见上）。原生参数做不到，参数副本可以。两句话
不矛盾，区别在于「原生参数」与「外挂传给原函数的参数」。

### 方向不能搞反（实测表）

split 下**请求的 `n_ctx` 是输入，窗口是派生**：`n_ctx_seq = PAD(n_ctx / S)`，随后把
`n_ctx` 改写为 `n_ctx_seq × S`。所以调用者若以「窗口」为输入，容量就必须取 `窗口 × S`，
而不是窗口本身。旧版把两者都当「容量 = 窗口」，于是**每一个不显式给容量的 split 请求都被
拒成 `split_would_round`**，而上游建得好好的——这比没有检查更糟，因为调用者分不清它与真限制。

真机实测（tiny transformer，`llama_n_ctx` / `llama_n_ctx_seq` 直读）：

| 请求 `n_ctx` | S | unified | 实际 `n_ctx` | 实际 `n_ctx_seq` |
|---|---|---|---|---|
| 6000 | 3 | 否 | 6144 | 2048 |
| 8000 | 3 | 否 | 8448 | 2816 |
| 8000 | 4 | 否 | 8192 | 2048 |
| 4000 | 4 | 否 | 4096 | 1024 |
| 4096 | 2 | 否 | 4096 | 2048 |
| 6000 | 1 | 是 | 6144 | 6144 |

由此：任何 256 对齐的窗口 W 都可由 `n_ctx = W × S` 得到（该值必然 256 对齐），所以
`split_would_round` 只在**显式要求更小容量**时才有意义——那种情况上游会把容量长上去，
是调用者没选的取整。

`explain()` 对不可表达的计划**永远**明说，哪怕数字看起来正是调用者要的：那正是调用者最可能
以为成功的场合。

## 补齐发生在比较之前

`pad256` 先作用于窗口与容量，再比较（分叉 `:976` 补齐、`:977` 比较）。所以：

- 4096 窗口 + 4000 容量 → 补齐成 4096 → **合法**（不是「小于窗口」）；
- 2000 窗口 + 8000 容量 + 4 序列 → 补齐成 2048 × 4 = 8192 = 8000 的补齐值 → **合法**；
- 2048 窗口 + 4000 容量 + 4 序列 → 补齐 4096 < 8192 → **拒绝**（`split_would_round`）。

我第一版测试把前两条判成拒绝，实现是对的、预期是错的。这三次失败本身说明判定站有用：
没有它，驱动只能靠猜。

## 已实测

```
cmake --build build --target tq_kv_capacity_tests   # 0 error（-Wall -Wextra -Wpedantic -Werror）
./build/modules/kv-capacity/tq_kv_capacity_tests    # "kv capacity contract holds"，exit 0
ctest -R tq_kv_capacity                             # 1/1 passed
```

用例覆盖：普通窗口、补齐的真实数字、精确长度模式、解耦接受与拒绝、split 精确/补齐后精确/
过短三种情形、**split 与真机上下文逐行对照**（6 组请求/实际值，见上表）、六条拒绝理由、
**门禁顺序**（架构先于范围、统一要求先于 arena 冲突，
因为前者的修法不是改数字）、`spare_windows` 是下取整且上下界都断言、以及每个拒绝理由
文案互不相同（两条理由共享一句话会把读者指向错误的修法）。

## 未做，且不得计为完成

- **实验 ≠ 产品**：机制已被 `patches/herd_nkv.cpp` 证明（参数副本让池子大于窗口，见上表），
  但该实验默认不进构建（`HERD_BUILD_NKV=OFF`）、不链接任何产品，`HERD_NKV_PHYSICAL` 未设时
  hook 根本不注册。要变成产品，缺的是验证而不是机制。
- **溢出**：本轮修掉了两处，因为它们是可证实的错误而不是观念问题：`pad256` 在窗口接近
  2^32 时会回绕（`(v+255) & ~255`），而比较发生在补齐之后，于是 4294967290 的窗口曾被
  判为「合法、上游可表达」，`logical = physical = 0`；split 分支的
  `aligned_window * sequences` 也是 32 位相乘，积一溢出，「请求超出形状」就变成「没超出」。
  现在范围检查在补齐之前，乘积用 64 位。两条都有回归用例。
- **未接任何驱动**：`batch-compose`/`rerot-compose` 仍按各自的拒绝路径工作；把它接进去是
  一步独立改动（先让 `--total-kv` 走判定站，再决定是接受拆分布局还是指名拒绝）。
- **本机边界**：解耦实验只在 CPU、单 buffer type、一个 llama-architecture 小模型上测过。
  未测：多设备/GPU；hybrid 与 recurrent 内存（它们按序列分配状态而非 cell 池，扩容对其无
  意义）；`n_seq_max > 2` 与 `kv_unified=false` 组合下的语义。这些是「未验证」，不是
  「不可行」——前两版把它们写成了后者，那是错的。
